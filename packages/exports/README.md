# @walkup/exports

Pure functions from a `StreetSheet` (see `@walkup/contracts`) to the files an operator takes away: the one-page Street Sheet PDF, the street-team calendar, four CSVs and `sheet.json`. No network, no clock (every date comes from the sheet), no disk writes. The same sheet always gives the same CSV, ICS and JSON bytes.

## Files

| File | Function | What it is |
|---|---|---|
| `street-sheet.pdf` | `toPdf(sheet, opts?)` | One page, US Letter (A4 with `pageSize: "A4"`): a day sheet for the street team with the partner table as a form (below). |
| `street-team.ics` | `toIcs(sheet, opts?)` | RFC 5545 calendar in two passes (about four weeks out, then the show week): one stop per partner inside its open hours on that day, a flyer drop for a numbered area with no partner to visit, plus the show. Each street-team day covers one part of town. |
| `partners.csv` | `partnersCsv(sheet, opts?)` | The call list: suggested partners (with the calendar's visit day, activation, why and confidence when the run built them), then the operator's own list in call order. |
| `zips.csv` | `zipsCsv(sheet, opts?)` | `zip, area, area_name, lift_score, suggested_weight`: the numbered areas' residential ZIPs; an area's ZIP weights add up to its share in the budget split. |
| `pins.csv` | `pinsCsv(sheet, opts?)` | `area, area_name, lat, lon, radius_km` (radius never under 1.6 km), one pin per numbered area. |
| `offer-codes.csv` | `offerCodesCsv(sheet, opts?)` | Promo-code rows to create in the operator's ticketing platform. |
| `sheet.json` | `toSheetJson(sheet, opts?)` | The whole sheet, ledger included, in a small versioned envelope. A sheet stored before Oct 20 2026 loses its Google Places comparison list first (`withoutControl`). |

`toExportFiles(sheet, opts?)` returns all of them (or `include: [...]`) as `{ kind, filename, contentType, data: Buffer }`, ready to attach to an email or zip. `prefix` goes in front of every name; the web downloads pass `exportFilePrefix(sheet)`, which names the headliner, the show date and the plan id's first 8 characters (`walkup-greensky-bluegrass-2026-12-30-455629e6-partners.csv`), so files from two sheets never share a name. Fixture sheets get a `fixture-` file-name prefix so a file never passes for a live run once it leaves the app; inside the files, the same plain sentence (`FIXTURE_NOTICE`: "Sample data: made-up places and numbers, not a live run.") is on the PDF (with a "Sample data" header label and one light watermark), in `sheet.json` as its `notice`, in every `partners.csv` row's `notes` and in each calendar description; calendar summaries and offer-code descriptions start with `[Sample] `. `zips.csv` and `pins.csv` keep the bare ad-platform format and rely on the file name.

### The PDF

It looks like a crew day sheet: black text on white, thin rules, one accent ink (the ticket-stub red `#b42318`) for the map tiles only, regular and bold Helvetica, sentence-case headings, no badges or pills. The web print page (`/s/[id]`) renders the same `buildSheetModel` strings with the same section names as the plan page ("Where this crowd stands out, compared with the room's usual crowd", "Before and after the show", "Partners (24)", "Your list", "What this sheet doesn't show", "Requests behind this sheet"), so paper, screen and PDF say the same things.

- **Header (day sheet):** top left "Walkup street sheet" (plus "Sample data" on a fixture sheet), the bill with the headliner in bold and the rest after "with" (`headliner`, `support`), then the age rule, street-team days and radius. Top right: the date (and the show's name when `showName` is passed), the room, "21 days to the show" (days from the plan's `createdAt` to the show; `asOf` overrides) and the counts as "n of m" ("640 of 1,200 seats left", "Capacity 4,400"), with "(assumed)" when a sample sheet's counts are what-ifs; "Counts are what-ifs" appears only on such a sheet that prints no count. What-if counts belong to sample (fixture) sheets only (`countsAreWhatIf`): a live sheet's counts are the operator's own, whatever an older stored sheet's `hypothetical` says. The age rule comes from Ticketmaster; the operator's `allAges` setting can only add to it ("All ages (operator setting)", "21+ (no bars: operator setting)"). One rule under the header. A thin signal is said once under it ("The signal is thin here, so treat this as a starting list."); the planning-tool note (sample what-if sheets only) is left out when the sheet's limits already say it.
- **Watermark:** one light diagonal line, "Sample data", on fixture sheets only. A live sheet has none.
- **Discovery line** (when `sheet.discovery` exists): "Start with this place: {headline}. {detail}" (or "Start in this area") with its receipts, and one muted "Why this one: ..." line under it (the full rule is on the system card). A picked partner the table marks less certain gets the same dagger after its headline; the dagger note is printed once, under the partner table, on the "+N more partners" line when there is one, so the note costs the one-page fit no line. A run that went through the pick and found none says "No top pick on this sheet:" ("after this change" on a revision) and why, read from the sheet by `noTopPick` / `noTopPickText` (the same words on the plan page and the print view): with no usual crowd, "both rules compare this crowd with the room's usual crowd, and this run has no usual crowd to compare with."; on a one-act bill, "the room's usual crowd ranks no partner here at least 5 places lower than this crowd does, and the area rule needs the map's split-half check, which can't run on a one-act bill."
- **Radius:** when the lift map's search widened past the operator's radius (`mapReachKm`, read from the map card's reason), the header says "radius 10 km; the map search widened to 60 km", the plan page's words, instead of "10 km radius".
- **Where this crowd stands out, compared with the room's usual crowd** (or with fans of the genre on a tag baseline; left) beside **Before and after the show** (right), with **Budget split** under the spots. The map is an SVG of geohash-6 cells about 60 mm wide, framed on the numbered areas and the venue, in the accent at the web maps' steps, with a light kilometre grid, a scale bar, ink circles with white numbers that match the list, and the venue as an ink square. Under it, the key in one line with the web legend's four steps ("under 1.0x", "1.0 to 1.3x", "1.3x", "2.2x and up") and a caption naming the baseline (`legendCaption`); with no usual crowd to compare with, the heading is "Where this crowd stands out", and on a sheet with no lift map (`noLift`) the key shows the venue square only. Beside it: areas 1-5 with lift and `blurb` (the residential ZIPs and the narrator's why line, cut at a sentence end at about 130 characters, the why's first sentence always whole; a ZIP list longer than three ZIPs takes no more of that length, so every area keeps the same sentences). The venue's name sits under its square, and the numbered markers keep clear of it. Under both: what the map is compared with and the split-half check. The spots are a small table, the local spots nearest to the venue first and then the national chains, as the card's "listed last" says, without food carts, kiosks, stands or food trucks (`sheetSpots`): spot (with receipts), type ("Bakery, national chain" on a chain, "Bar, not for fans" on an operator-only spot), distance in km (rounded from the plan page's 10 m figure under 1 km, so 950 m is 1.0 km), share of the crowd (only when the shares differ, `showShare`, with the capacity assumption said once in `shareNote`), and the rank for this crowd against the usual crowd ("3 places higher", or "not in its list" for a spot the usual crowd's list does not have; the column is left out when no spot has a rank, `showVsUsual`), and the age policy. The budget split is by area number, each area with its own stored share and dollars, the plan page's numbers (`areaBudget`, the same weights as zips.csv), the shares to one decimal so they add up to 100.0%.
- **Partners, as a form** (full width): a tick box, the row number, the place (name and type, "Cafe, national chain" on a chain, then the address, then the phone on a line of its own and never cut, or "Phone not listed", with the website's domain when there is one), the area's map number and name ("near venue" for a place from the search around the venue), the visit day and its hours ("Visit day": the day street-team.ics visits the partner and that day's own hours, "Sat 10 am to 2 pm", the same weekday in both passes, or both weekdays, each with its own hours, when a holiday's stops moved to another day of its week or a stop moved off a day with no time left for it; with one street-team day, "Open Thu" and that day's hours; "Hours not listed: call first" or "Closed Thu and Sat" on a pale yellow row, the one thing to act on), the why line with its receipts ("Ranks 8th here for this crowd, 20th for the room's usual crowd."), and a Notes column (22% of the width), blank but for a partner street-team.ics has no time left for: "No time left on the route: call to arrange", or "No time left on the first pass: call to arrange" when the other pass times it (the model's `routeNote`; `hours` ends with it, for the plan page, the print view's phone-width rows and the email, and `dayHours` is the hours alone, which the print view's table shows with the note in its Notes column, as the PDF does). Rows are 7 mm tall at full size. Receipts are one quiet, sorted group per row (`receiptGroup`: "Q6-Q7, Q13 +2"). Footer: "Suggested, not affiliated: no partner has agreed to anything." With `audience: "fan"` on a show not known to be 21+, bars are left out and counted.
- **Podcasts and a sponsor** (at most 3 podcasts on the PDF, `PDF_MAX_PODCASTS`, with the rest counted beside the heading, "+1 more podcast on the plan page"; the print view lists up to 4; then the sponsor, or why there is none when the status line doesn't already say it) beside **Copy lines** (at most 3, with the alcohol-word count and the tag note), under the partner form.
- **Foot of the page, three columns:** "Your list" in call order (ranked first, then "not in Qloo's catalog, kept in your order"); "What this sheet doesn't show" (`sheet.limits`, or `LIMITS_EVERY_SHEET` when empty; every sheet prints them); "Requests behind this sheet" ("34 requests: Q1-Q32, T1-T2. Receipts for every Q number: {ledgerUrl or sheet.json}. Plan g1-a.", a link when `ledgerUrl` is absolute), a line pointing to the calendar and, when the sheet has numbered areas, the ad files (`footer.elsewhere`), and the data credits; on a fixture sheet the credit line says the data is a sample shaped like Ticketmaster and Qloo answers. "Sample" appears only in the header, the footer line and the watermark.
- **One footer line** (`footer.printLine`): "Hollis Creek String Band · The Truth · Fri Nov 20 · printed Wed Oct 14 2026 · data from Fri Oct 30 2026 · Sample" (the last word on fixtures only; `printedAt` overrides the clock).
- **Sections:** `SheetModel.sections` (`PAGE_SECTIONS`: map, spots, partners, media, hooks, budget, declared, limits, requests) is the one list both the PDF and the print view (`/s/[id]`) print, so the downloaded PDF and the printed page carry the same sections.

**Fitting one page.** `renderStreetSheetPdf` renders at full size with 7 mm form rows, then at smaller type (down to 74%), cutting the partner rows (16, 14, then 20 and 16 at the smallest type) before every list is shortened (12 partners, 6 declared, 6 spots, 3 podcasts); omitted rows are counted on the sheet ("+N more partners in partners.csv", "+1 more partner in partners.csv"). It returns `{ buffer, pages, scale, truncated }`. `fit: false` renders once at `scale`.

**Text.** The PDF uses the built-in Helvetica faces, which only draw Windows-1252 characters. Every string goes through `pdfText`: arrows and maths signs get ASCII stand-ins, accented letters outside the set lose the accent, anything else becomes `?`.

The tree is plain `React.createElement` calls on react-pdf primitives (no components, no hooks): `streetSheetDocument(sheet)` returns it, `buildSheetModel(sheet)` returns every printed string, and both are tested without rendering. `buildSheetModel` is also exported on its own as `@walkup/exports/sheet-model`, so a page can use it without loading the PDF renderer.

### The calendar

- **Two passes** (`streetTeamPasses`): a first pass on the street-team days (`streetTeamDays`, default the sheet's) 22 to 28 days before the show (`firstPassWeeksOut`, default 4) to leave flyers and ask for a poster, and a final pass in the show week (the 7 days before it) to restock flyers, with shorter stops (`finalPassMinutes`, 10). No one goes out on a holiday (`streetTeamBlackout`: Thanksgiving, Christmas Eve and Day, New Year's Eve and Day, Independence Day), when shops keep holiday hours: that day's stops move to the same weekday a week earlier (two weeks when that is a holiday too; never before the plan's creation date or, in the final pass, onto the first pass), so both passes keep the same days, each partner keeps its weekday and that day's hours, and the pass's earliest event says "No street team on Thu Dec 24 2026 (Christmas Eve): shops keep holiday hours. Its stops are on Thu Dec 17 2026 instead." (`streetTeamHolidays` lists each holiday and where it moved). A final-pass day moved out of the show week says "Final pass, 2 weeks out". When neither is free (the plan was made later, or the day is not after the first pass), the stops move to the nearest free day of the holiday's own week, earlier first ("Its stops are on Wed Dec 23 2026 instead"), so the pass still has as many days as the other and no day takes two days' stops; that day keeps its own weekday and hours, a partner closed then is "Not scheduled, closed on Wed and Sat" for that pass, and a partner the passes visit on two weekdays shows both in the Visit day column, each with its own hours. Only when the whole week is taken does the final pass go a day short ("Its stops are on the pass's other days"); a first pass that would moves a week closer, or there is only the final pass. No date is before the plan's creation date (`notBefore` overrides): a first-pass week that starts earlier moves one week closer, down to 8-14 days out, and when no whole week fits there is only the final pass. `firstPassWeeksOut: 0` gives the show week only. With two passes, summaries say "Street team, first pass: ..." / "Street team, final pass: ..." and each description starts with what the pass is for.
- **Days by part of town:** the numbered areas (with their partners; partners outside them grouped by their own tile) are put in nearest-neighbour order from the venue and cut where the route jumps furthest into one run per street-team day (each day between half and one and a half times its share of stops), so a day covers one part of town and an area's partners share a day. An area moves to another street-team day when more of its partners are open then and both days stay inside that band. Both passes use the same days, unless a holiday moves to another day of its week (see Two passes).
- Each partner is one stop per pass on a day it is open: its area's day when it is open then, else another street-team day of the pass when it is, else the first day its hours aren't listed, marked "call first" in the summary and description. Hours come from the place's own week (`entity.properties.hours`, read per day by the engine's `hoursOnDay`), so a Saturday stop is timed and labelled with Saturday's hours; the sheet's `hoursOnDay` text is used only for the day it belongs to (the first street-team day). A partner listed closed on every street-team day is not scheduled; its area's earliest event of each pass says "Not scheduled, closed on Thu and Sat: ..." (when the pass times nothing in that area, the event that lists the area's stops with no time left says it, else the earliest event of the area's day). A numbered area with no partner to visit gets a flyer drop (`visitMinutes`, 90).
- Times: each day starts at the venue at `startTime` (10:00), stops of `stopMinutes` (20), with travel between them (2 minutes per km, at least `gapMinutes`, 15). Each step takes, among the stops that can start within 45 minutes of the soonest one, a stop in the same area when there is one, else the nearest (a nearest-neighbour walk), never one that would leave another stop no time inside its hours. Every stop with listed hours lies inside them, including a partner open only before `startTime`; nothing runs past 23:59. No two stops overlap and every hop allows its travel time: a stop the day has no time left for goes in a free stretch between two stops when one is long enough, else to another street-team day of the pass where it fits whole inside that day's hours (a partner the first pass moves keeps that weekday in the final pass); with no such day it is not timed at all, and the day's earliest event says "No time left on the Sat Dec 19 2026 route for: {partner} ({area}), {address}, {phone}, open Sat {hours}. Call to arrange a drop-off another day." (`notTimed`; partners.csv marks that date in `visit_dates`, and the partner's row on the sheet says it, see the partner table above). On the recorded sheets this happens only on the plans with one street-team day and 18 to 24 stops, when that day is full. A day with nothing timed at all gets one all-day event that says it instead ("Street team, first pass: no time left for 1 stop"; `planStreetTeam` returns these days as `notes` beside the timed `visits`).
- Each stop: SUMMARY ("Street team: {partner} (area 1, Silver Spring, MD)"), LOCATION (the partner's name and address), GEO (the place, else the tile centre), DESCRIPTION (area, lift and ZIPs; the partner with address, phone and that day's hours; its activation line; the "suggested, not affiliated" line; receipts), `STATUS:TENTATIVE`. The show is an all-day event, or a timed one with `showStartTime`.
- Area names everywhere (calendar, PDF, web sheet, CSVs) are `areaLabel(tile)`: the area's own name and its own state, from the area's own point, else its ZIPs ("Silver Spring, MD", "Arlington, VA", "Georgetown, DC"), never the venue's city.
- CRLF line endings, lines folded at 75 octets without splitting UTF-8 characters, TEXT escaped (`\\`, `\;`, `\,`, `\n`).
- UIDs are `hl-{planId}-{yyyymmdd}-{geohash}-{entityId}@walkup` for a stop and `...-{geohash}-flyers@walkup` for a flyer drop (`uidDomain` overrides) and the show's `hl-{planId}-show@...`; re-importing an updated plan updates events instead of duplicating them. DTSTAMP is the plan's `createdAt`.
- **Time zones:** times are floating local times by default (no TZID): "10:00" means 10:00 on the wall clock wherever the calendar is opened, which is right for a street team in the venue's city. Pass `timeZone` with one of `SUPPORTED_TIME_ZONES` (America/New_York, Detroit, Chicago, Denver, Phoenix, Los_Angeles, Anchorage, Pacific/Honolulu) to pin times with a VTIMEZONE using the US rules in force since 2007. Other zones fall back to floating times rather than inventing rules. Without `timeZone`, `toIcs` uses `sheet.bill.venue.timeZone` (Ticketmaster's venue timezone, filled by `@walkup/tm`), so sheets made from a Ticketmaster event get a VTIMEZONE when the zone is supported.

### The CSVs

All CSVs follow RFC 4180: header row, CRLF after every record, a field quoted only when it holds a comma, a double quote, CR or LF, inner quotes doubled. Output is UTF-8; `bom: true` adds a byte order mark (`toExportFiles` adds one to `partners.csv` and `offer-codes.csv`, which people open in spreadsheets, and never to `zips.csv` or `pins.csv`). Text cells that a spreadsheet would run as a formula (`=`, `@`, or `+`/`-` followed by anything other than a plain number or phone number) are prefixed with `'`; numbers are never touched. `formulaGuard: false` turns this off.

- **partners.csv** columns: `call_order, list, name, category, tile, tile_lift, address, day, hours_on_day, visit_dates, phone, website, contact_email, activation, why, confidence, affiliation, receipts, chips, qloo_entity_id, qloo_rank, score, called, outcome, notes`. `category` says ", national chain" on a chain and `tile` "near venue" for a place from the search around the venue, as the paper does. `day` and `visit_dates` come from the same plan as street-team.ics (`partnerVisits`; `toExportFiles` passes its `ics` options to both; a date the route had no time left for reads "2026-12-05 (no time left on the route: call to arrange)"), and `hours_on_day` is that day's hours ("Sat 10 am to 2 pm"), "Hours not listed: call first", or "Closed Thu and Sat: not on the calendar". `phone` says "Phone not listed" and `website` "Website not listed" when there is none, as the paper does; `website` is the cleaned one only (`Partner.website`, the same as the plan page and the PDF), never a raw Qloo site the engine's rule dropped. When the place's record has a link the rule dropped, `website` says why instead (`websiteNotShown` from `@walkup/engine`): "Website not shown: the listed link doesn't work" or "Website not shown: the listed link doesn't match the place's name". `contact_email` is only ever an address the operator typed on their own list. `activation`, `why` (tags, then "High confidence: ..." and the explain limits) and `confidence` come from `partner.explain` and are blank without it and on the operator's own list. A row from the operator's own list takes `category` from the place's Qloo record ("Not in Qloo's catalog" when Qloo has none), `tile` "Your list: not tied to an area" (offer-codes.csv says the same) and `hours_on_day` from the record; `day`, `visit_dates`, `score` and the explain columns stay blank, since that list is not searched by area or routed. `called`, `outcome` and `notes` are blank for the street team to fill in (`notes` carries the sample notice on a fixture sheet).
- **zips.csv:** the numbered areas (lift >= 1.3, at most 5; `maxTiles` and `minLift` override) and their residential 5-digit ZIPs, in area order, a ZIP in two areas once under the first. ZIPs that are not homes (P.O. boxes, one organisation, a campus) are dropped by `isResidentialZip` from `@walkup/gazetteer/zips` (the `isResidentialZip` option replaces it); the sheet's ZIP lines and the calendar use the same rule. Each area's weight (`tileWeights`) is its own share of the sheet's budget split when the split covers every area (the plan page's numbers), otherwise proportional to lift; an area's weight is split evenly over its ZIPs, so an area's rows add up to its share in the PDF's budget split (scaled up when an area has no residential ZIP to list), and the rows are rounded to 4 decimals summing to exactly 1. ZIPs stay text, so leading zeros survive.
- **pins.csv:** one row per numbered area: its number and name (`area`, `area_name`), the tile's centre to 5 decimals, and `radius_km` = half the cell's diagonal rounded up to 0.1 km, never below 1.6 km (one mile; `minRadiusKm` can raise it).
- **offer-codes.csv** columns: `offer_code, description, channel, assigned_to, tile, event_id, event_date, venue, valid_from, valid_until, discount, max_uses, status`. One code per suggested partner, per declared entry and per top tile, built from the partner's or tile's own name plus a running number (`LOWHUM01`), with an optional `codePrefix`. A partner's `tile` is the same words as partners.csv and the paper ("Kenilworth, DC (place in MD)", "near venue"), and its description says them too ("Street team code for Oasiz Bar & Grill (Kenilworth, DC, place in MD)"). Codes and descriptions never carry act names. `discount` and `max_uses` are blank: pricing is the operator's call. Every row's `status` is "create in your ticketing platform": nothing is created anywhere by this package.

**Loading the ad files.** Neither file carries an audience label: a ZIP or a pin and a weight, nothing about who lives there. The operator sets targeting in their own ad account. At the time of writing:
- Meta Ads Manager: in the ad set's Locations, "Add locations in bulk" takes a pasted list of ZIP codes (country United States). Pins are dropped one per row; set the radius unit to km.
- Google Ads: in the campaign's Locations, "Advanced search" has "Bulk locations" for the ZIP list and "Radius" for each pin; Google Ads Editor can import both.
- Neither platform reads `area`, `lift_score` or `suggested_weight`; use the weight to split budget across ad sets (one ad set per area: add up its ZIPs' weights) or as a manual bid adjustment. Bulk-entry formats change; check the platform's current help page and rename columns if it asks for different headers.
- Opening `zips.csv` by double-clicking it in a spreadsheet can drop leading zeros (02134 -> 2134); import the column as text instead.

**Ticketing platforms.** The offer-code columns follow the fields TM One and Etix promo codes have (code, description, start and end dates, discount, usage limit); the names differ per platform, so map them when creating the codes.

### sheet.json

`{ format: "walkup.street-sheet", formatVersion: 1, planId, mode, hypothetical, notice?, sanitized, sheet }`. `sheet` is the full StreetSheet with its ledger. `notice` is set on fixture sheets. `hypothetical` (on the envelope and in `sheet`) is true only on a sample sheet with what-if counts, never on a live sheet. Before writing, `sanitizeSheet` re-applies two rules the pipeline already enforces, because this file is persisted and shared: denied tags (`isDeniedTag` from the engine) are removed from every tag list and tag-id list, person entities lose all tags, and ledger params or copy-as-curl strings holding a literal credential (anything not a `$ENV_VAR` reference) are replaced with `[redacted]`. `sanitized` reports the counts (zero when the pipeline did its job). `sanitize: false` skips the pass.

## Public API

Everything is exported from `src/index.ts`.

- PDF: `toPdf`, `renderStreetSheetPdf`, `streetSheetDocument`, `streetSheetElement`, `countPdfPages`, `PAGE_SIZES`, `PDF_MAX_PODCASTS`.
- Model: `buildSheetModel` (options: `audience`, per-panel caps, `ledgerUrl`, `asOf`, `showName`), `sheetModelText`, `partnerHoursColumn` (the partner hours column, the same rule for the paper, the CSV, the calendar and any page or email that uses it), `spotColumnWidths`, `noTopPick` / `noTopPickText` (why a sheet has no top pick, for the PDF, the print view and the plan page), `podcastsOmittedText` ("+1 more podcast on the plan page and in sheet.json."); also `@walkup/exports/sheet-model`.
- Map geometry: `layoutTileMap` (with `unitsPerKm` for the grid and scale bar, and `venueLabel` when given the venue's name), `placeLabels`, `venueLabelSpot`, `venueLabelBox`, `liftBand`, `liftAlpha`, `liftFill`, `niceKm`, `LIFT_INK`, `MAP_COLORS`, `LABEL_RADIUS`, `MIN_VISIBLE_CELL`.
- Calendar: `toIcs`, `planStreetTeam`, `planStreetTeamVisits`, `streetTeamPasses`, `streetTeamHolidays`, `streetTeamBlackout`, `isStreetTeamBlackout`, `partnerVisits`, `NO_TIME_ON_ROUTE`, `streetTeamDates`, `FIRST_PASS_WEEKS_OUT`, `escapeIcsText`, `foldLine`, `icsLocal`, `icsUtc`, `vtimezoneLines`, `SUPPORTED_TIME_ZONES`.
- CSV: `toCsv`, `csvCell`, `looksLikeFormula`, `partnersCsv`, `partnersCsvRows`, `declaredInCallOrder`, `zipsCsv`, `zipRows`, `pinsCsv`, `pinRows`, `offerCodesCsv`, `offerCodeRows`, `tileWeights`, `areaBudget`, `apportion`, `geohashHalfDiagonalKm`, `MIN_PIN_RADIUS_KM`, and the column lists.
- JSON: `toSheetJson`, `sheetJsonDocument`, `sanitizeSheet`.
- Bundle: `toExportFiles`, `exportFilePrefix`, `EXPORT_FILE_NAMES`, `EXPORT_CONTENT_TYPES`.
- Fan-facing rule: `isFanFacing`, `spotIsFanFacing`, `partnerIsFanFacing`, `fanFacingSpots` (`@walkup/exports/audience`, safe for client components). The sheet model's fan version and its "not for fans" marks use it; the plan page's "Show what fans see" should too.
- Helpers: `pdfText`, `isPdfSafe`, `topTiles`, `areaLabel` (the state goes before a trailing distance: "Des Plaines, IL, 19 km northwest", as on the plan page), `withState`, `DISTANCE_SUFFIX`, `areaState`, `partnerAreaLabel`, `partnerAreaText`, `NEAR_VENUE`, `spotVsUsual`, `PHONE_NOT_LISTED`, `WEBSITE_NOT_LISTED`, `HOURS_NOT_LISTED`, `formatPhone`, `tMinusDays`, `tMinusLabel`, `formatShowDate`, `ledgerRanges`, `actsLine`, `sheetAgeLabel`, `isAllAgesForCopy`, `explainTags`, `partnerWhy`, `partnerWhyLong`, `TOP_LIFT`, `SUGGESTED_NOT_AFFILIATED`, `ATTRIBUTION`, `FIXTURE_NOTICE`, `SAMPLE_LABEL`, `SAMPLE_PREFIX`.

Server-side only: `toPdf` needs Node (`Buffer`). In a Next.js route, import it from server code; if the bundler trips on react-pdf, add `@react-pdf/renderer` to `serverExternalPackages`.

## Test

```
npx vitest run packages/exports
npx tsc -p tsconfig.json --noEmit 2>&1 | grep "packages/exports"
```

Test sheets are built in `test/helpers.ts` (invented acts, venue, businesses and ids). The PDF tests render real PDFs, inflate the content streams and read the text back (`test/pdf-text.ts`), walk the React tree, check page size and the one-page fit, and render every sheet in `fixtures/synthetic/` when present. The ICS tests unfold and check CRLF, the 75-octet limit, required properties, UIDs and zones; the CSV tests read the output back with a strict RFC 4180 reader (`test/csv-parse.ts`).

## Known limits

- No QR code on the PDF (no QR library is installed); the ledger line carries a link instead when `ledgerUrl` is absolute.
- No basemap or city outline under the tiles: geohash cells, a kilometre grid, a scale bar and the venue only.
- The paper table has no Activation column (it is in `partners.csv` and on the web sheet's "Why this place").
- The numbered areas (`topTiles`) skip a tile within 3 km of, or sharing a ZIP with, a higher one, the same rule as the orchestrator's spread tiles, so map numbers, partner areas and the budget split agree. Map labels closer than about two marker widths merge into one ("3, 4").
- Standard fonts only: names outside Windows-1252 (for example Vietnamese or CJK) print transliterated or with `?`. Embedding a Unicode font would fix this at the cost of shipping one.
- Partner hours on the PDF and in partners.csv are for the partner's visit day in the calendar (the first street-team day when there is only one).
- An area's state comes from the area's own point (`tile.state`, from `stateForPoint` in `@walkup/gazetteer`: the ZIP prefix of the smallest ZCTA, read as a circle of its land area, that holds the point), else from its ZCTAs (`@walkup/gazetteer/states`). Georgetown is DC though its nearest ZIP is in VA; an area right on a state line can still get its neighbour's state.
- ZCTAs approximate ZIP codes; a few ZIPs (PO boxes, single buildings) have no ZCTA.
- ZIPs the operator already reaches (`operator.alreadyReachedZips`) are not down-weighted.
- The fit loop can render up to six times on an overfull sheet (about 1-2 s); a normal sheet renders once.
- `countPdfPages` counts page objects in this renderer's uncompressed object table; it is not a general PDF parser.
- `sanitizeSheet` scans arrays for tags and tag ids; a denied tag inside a free-text string is not caught there (the narration guard owns free text).
