# @walkup/orchestrator

Runs one plan end to end and returns a `StreetSheet`: Ticketmaster intake, Qloo resolution (Q1-Q3), the plan graph (Q4-Q14) with typed fallbacks, deterministic scoring from `@walkup/engine`, narration from `@walkup/narrator` under two guards, the provenance ledger and plan storage. No comparison arm runs: the Google Places "Without Qloo" arm (F) was removed on Oct 20 2026, and nothing here calls Google. Server-side only (it imports `@walkup/qloo`, which loads `better-sqlite3`).

## Quick start

```ts
import { createFixtureDeps, planShow, PRESETS } from "@walkup/orchestrator";

const deps = createFixtureDeps();            // fixture world, mode "fixture", template narration
const r = await planShow({ presetId: "g1-a" }, deps, {
  onCard: (key, envelope) => stream.write({ key, envelope }), // SSE, in CARD_ORDER
  onStep: (step) => stream.write({ step }),                   // one TraceStep per decision, as the run reaches it
});
if (r.status === "needs_input") {
  // r.pause.pending: [{ input: "Sidecar", candidates: [...] }]
  await planShow({ presetId: "g2", planId: r.planId, resolutions: { Sidecar: chosenId } }, deps);
}
r.sheet;   // StreetSheet with cards, narration, ledger, guard, budgetSplit, limits, steps, discovery
r.budget;  // Qloo calls sent vs cached, bill-level vs venue-level
```

With keys, `createDepsFromEnv()` returns live clients (`mode: "live"` only when `QLOO_API_KEY` and `TICKETMASTER_API_KEY` are set and `WALKUP_MODE` is not `fixture` or `recorded`); otherwise it returns the fixture deps. A sheet never says `live` unless real keys and live transports produced it.

## Public API

| Export | What it does |
|---|---|

Returns `PlanResult` (`status: complete | needs_input | error`, `sheet`, `pause`, `budget`, `citations`, `servedFromStore`, and `ledger` when a run stopped with an error after making calls). `opts` (`PlanOptions`): `onCard`, `persist`, `serveFromStoreWhenGuarded`, `onStep` (each step of `sheet.steps` as the run reaches it; a paused run streams its pause step, which no sheet holds) and `revise` (set by the revise loop). |
| `revisePlan(parent, note, deps, opts)`, `readInstruction(sheet, note, deps)`, `runRevision(parent, reading, deps, opts)` | The revise loop (below). `parent` is `{sheet, request}`. |
| `parentRequest(sheet, {stored?, presetId?})`, `revisedRequest`, `overridesFor`, `diffSheets`, `reviseSummary`, `sheetAreas`, `reviseStep`, `questionRevision`, `pausePicks` | Its pieces, exported for the web app, MCP and tests. |
| `CARD_ORDER` | resolution, liftMap, partners, declared, prePost, media, demographics, whatsDifferent, copyHooks. |
| `PRESETS`, `presetById`, `PRESET_IDS`, `presetFor`, `presetShowOf`, `NO_LIVE_SHOW` | G1-A, G1-B, G2, G3, G4-A, G4-B: venue, the bill the selection rule picked, operator what-ifs, seed plans. The top-level fields are the fixture show: every bill there is invented. G4-A and G4-B have no fixture show of their own: in fixture mode they plan G1-A's and G1-B's invented bills (`fixtureSameAs`). `live` holds a real Ticketmaster bill (event, venue, as-of date, title, selection, real-only operator inputs, line): g1-a and g1-b at The Anthem, Washington DC, and g4-a and g4-b at The Salt Shed, Chicago; it is null for g2 and g3. `presetFor(preset, mode)` is the one reader: the fixture fields in fixture mode, the live block in live mode (`realShow: true`), or null in live mode while `live` is null, and `planShow` then stops with `NO_LIVE_SHOW` ("This preset has no live show yet.") before any Ticketmaster or Qloo call. `presetShowOf(preset, mode, bill)` is that show only when `bill` is its event: the quota guard's stored-sheet fallback and a revision's preset request use it, so a run recorded before `live` changed is never served or re-run as the new show. | `createFixtureDeps(opts)` | Real clients on `@walkup/qloo-world` transports, in-memory SQLite Qloo cache, fixed or injected clock. |
| `createDepsFromEnv(env, opts)`, `liveKeysPresent(env)` | Live deps when keys exist, else fixture deps. |
| `createMemoryPlanStore()`, `getPlan(store, id)` | Plan storage (memory). A `PlanStore` has `put`, `get`, `latestForPreset`, `list` and `listComplete({presetId?, mode?}, limit)` (complete plans, newest first). |
| `createSqliteStores(file)`, `createSqlitePlanStore(file)` from `@walkup/orchestrator/sqlite` | SQLite: table `plans(planId, createdAt, mode, json)` and the operator's cached picks (`choices`). |
| `createMemoryChoiceStore()` | Picks cached per (query, types) for 30 days. |
| `loadTagPins(file)`, `defaultTagsFile(env)`, `TagPins` | Pinned URNs from `config/tags.json` (unpinned entries skipped). The file is `WALKUP_TAGS_FILE` when set, else the nearest `config/tags.json` above this module or the working directory (a bundled server finds the repository, or `/app` in the image, that way). |

Deps (`PlanDeps`): `qloo` (shared client; each run uses `withLedger`), `tm(ledger)`, `acs(ledger)` (no step calls it since arm F was removed; adult counts come from the gazetteer), `gazetteer`, `narrator: { client, spend }`, `ledger()`, `clock`, `idGen`, `store`, `choices`, `tags`, `probes`, `mode`.

## The run

1. **Intake.** Ticketmaster event to `Bill` (`legalAgeEnforced` from `ageRestrictions` only), or an operator-entered bill. Operator inputs: preset values, then request overrides; radius 40 km by default. Operator-typed contact emails never reach Qloo, the sheet or the store (the confirm-gated send gets them from the operator directly). Three inputs only remove things: `excludeAreas` (tile geohashes or gazetteer names, any case) leaves those areas off the lift card's top list and out of the partner pools; `excludeCategories` drops those partner categories; `allAges: true` drops every bar category from the partners and excludes night clubs at the Q9 request even when Ticketmaster says 21+ (`false` or absent never relaxes Ticketmaster's rule).
2. **Resolve.** Q1: one `/entities?external.spotify.ids=` call, then typed `/search` (artist, person; exact normalized name; comedians need the comedian tag). A one-word name with several exact matches always asks (`needs_input`); an artist entry and a person entry for the same musician (`sameAct`) count as one match. The run pauses, is stored, and resumes with the pick (cached for 30 days, only when the pick was one of the candidates shown, and only after the signal check accepts it). A failed search reads as a failure on the card, never as "no match". Only thin acts (popularity under 0.35) use declared film/TV proxies (release year checked); an act Qloo knows well is always its own seed (Oct 15, probes 6 and 7), and nothing is weighted (POST weights returned 400, probe 14). Q2: venue by name within 1 mile, else the Ticketmaster point. Q3: the room's next 60 events, top headliners by recency, Spotify ids then at most 6 typed searches; fewer than 5 resolved means the pinned genre tag baseline, which comedy never gets (`baselineTagFor`: the comedy tag map was empty on Oct 15, probe 19).

   **Signal check** (`Q1 signal check`, `steps/resolve.ts`). Qloo can list an entity under `/search` and still have no taste data for it (Oct 15: the "Jason Isbell" artist entry; "Jason Isbell and The 400 Unit" works). Heatmaps, tag profiles and compare drop such an id silently, so after Q1-Q3 one `ctx.qloo.checkSignals` pass (place insights at the venue, 1,500 m, `take=1`; one call per 25 ids, plus one more per Spotify-matched act Qloo drops, which is searched by name and checked again; a 200 is cached 7 days, a 400 is not cached) covers every act pick, up to 2 fallback entries per act from the same search (`signalAlternates`: other exact matches of the same type, billing names like "<name> and ...", then the other type), the needs_input candidates, the stand-ins and the house ids. A dropped act moves to the one usable fallback (row `exact` with `replaced`, a line on the card, a cause in the acts step), asks when several fit (`needs_input` with a `reason`), or is left out (`unresolved` with a `reason`). A dropped operator pick is deleted from the `ChoiceStore` (`delete`) and the operator is asked again. Dropped house ids and stand-ins are left out (below 5 house ids, the tag baseline). A failed check adds a sheet limit and the run goes on unchecked. Later place calls read `meta.droppedSignals` as a safety net: a list built on no usable seed is never shown as this bill's ranking (`droppedFrom`, `droppedReason`).
3. **Plan graph.** Q4 bill heat (fewer than 200 cells: 60 km, then `partial: thin`), Q5 house heat (roster; when it fails or comes back empty, the pinned genre tag stands in and the card says why; a comedy bill with neither gets no lift map, `degraded`, and no Q6 call), Q6 generic heat for the lift diagnostic, lift (engine: bounded score `(bill percentile + 0.5) / (house percentile + 0.5)`; top tiles need lift 1.3, bill percentile 0.7 and adults above the floor), then the **split-half check** (below), Q9 partners in the top 3 tiles at least 3 km apart (2,000 m, then 3,500 m, then wider categories; with fewer than 3 usable tiles the rest of the list comes from a near-venue pool, and with none, from the near-venue pool alone), each pool's **house twin** (below), Q11 declared partners (pick-list search for typed names, cap 20, then `filter.results.entities`), Q10 pre/post (1,500 m then 2,500 m; house-signal twin for the delta rank; a spot whose hours are not listed for show night is kept with the chip "near the room, no hours listed for show night: call ahead" and counted on the card, never shown as open), Q12 podcasts and Q13 one sponsor with `signal.location` (both answer 200 with 15 rows on a usable seed, Oct 15; national unless the probe says local; alcohol/tobacco/gambling excluded on shows that are not 21+ by pinned tags when they exist and always by the brand's name and tags), Q7 demographics, Q8 compare (empty or failing: two `urn:tag` profiles diffed by rank, `degraded: tag diff`; no usual crowd and no genre tag: `empty`, no call), Q14 the copy allowlist. `/v2/audiences` is not used (it returned nothing on Oct 15).
4. **Score.** Engine partner scoring with the diversity caps and the ubiquity penalty, national chains after local places (both lists; `src/chains.ts` bundles the hand-kept [`config/chains.json`](../../config/chains.json), so live and fixture runs use the same list; the card adds the chain sentence (`chainSummary`: "2 of 16 partners are national chains, listed last in their area: no local place filled their slot. 12 more chains left off: 10 for local places, 2 by the limit of 2 per list.") and the chain limit (a hand-kept list, Qloo's description, a store-locator website or the same name or website at 3 or more places, `chainSignals`; a chain none of these catches is listed like a local place) when any eligible candidate is a chain, and the step names the chains that fell off), pre/post load balancing (outing rate 0.2, assumed capacity 120), budget split over the top tiles. Operator "already reached" ZIP counts down-weight tiles locally and are never sent anywhere.

   **Split-half check** (`steps/heat.ts`, `runSplitHalf`). The bill's seeds and the house's roster ids are each split into two disjoint halves by `@walkup/engine` `splitHalves` (FNV-1a order, dealt alternately). Four more heatmaps at the same point and radius: `Q4 bill heat, half 1|2 (split-half check)` (bill-level) and `Q5 house heat, half 1|2 (split-half check)` (venue-level, so bill B at the same room reads them from cache). Lift per half, then Spearman between the halves on the tiles all four maps share. Written to `cards.liftMap.results.liftDiagnostics` as `{ splitHalfSpearman, liftVsHeatSpearman, billFloor: 0.7, method, note? }` (the old `results.diagnostics` is unchanged); every half's ledger id is in the card's provenance. At or below 0.5 the card is `partial` with "The two halves of the bill put this crowd in different areas (agreement 0.42, 0.5 needed), so partners are picked near the venue." and partners are ranked near the venue, as when lift tracks raw heat (Spearman above 0.9) or ranks areas almost like the bill's own map (`spearmanLiftVsBillHeat` above 0.9, the KG2 statistic; the card says the map shows where the crowd is, not where it stands out). Typed fallbacks, each with a plain `note` and no effect on the map: one seed (no calls, null), a genre-tag baseline (only the bill is split: 2 calls), a failed or empty half (null, the failed call stays in the ledger), fewer than 3 shared tiles (null).

   **House twin and ubiquity penalty** (`steps/partners.ts`). After each Q9 pool settles (fallbacks included), `Q9 house twin, tile N` replays the same request (tile point, radius, category tags, street-team hours, price cap, exclusions) with the house signal the Q10 twin uses (roster ids, else the genre tag) and no explainability. Bill-level: its point is the bill's tile. The engine turns the twin's ranks into `Partner.houseRank` (null when the place is not in the twin's list) and `Partner.ubiquityPenalty` (0 to 0.5, already applied to `score`; formula in the engine README), and the step adds a chip citing the twin (`usualCrowdChipLabel`: "ranks 3 places higher here than for the room's usual crowd", "ranks the same here as for the room's usual crowd", or "not in the room's usual crowd's top N"), plus a card limit line. A failed or empty twin leaves that pool without a rank, a penalty or a chip, and the card reason says so (an empty list is no evidence that a place is missing for the usual crowd). The run passes the house set from `runHeat` (`houseFor(ctx)`) unless the caller gives `runPartners` one.

   **Popularity twin and the popularity check** (`steps/partners.ts`, `runPopularity`). Once the partner list is final, each pool that gave partners gets `Q9 popularity twin, tile N` (or `near venue`): the pool's final request (tile point, radius, category tags, street-team hours, price cap, exclusions, `take=50`) with no `signal.interests.entities` and no explainability, which Qloo answers in popularity order (probe 1 / KG1, Oct 15). Bill-level, cached like any insights call. `@walkup/engine` `popularityCheck` then counts, per area, the partners that are not among the twin's first k places that pass the same eligibility rules as scoring (k = partners picked in that area). The result is `sheet.popularityCheck` (`{ partners, notInPopularTop, perArea[], ledgerRefs }`), the twin refs join the partners card's provenance with the limit line "The popularity check runs the same Qloo search ... It compares two lists, not ticket sales." (it says "near the venue" instead of "in each area" when every pool was near the venue), and the "Popularity check" step says the number. The check never changes the list. A failed or empty twin (any area) means no number: no field, no limit line, nothing on the card, and the step says which area and why.
5. **Balance check** (probe `explainabilityInformative`): one seed above 0.7 of explainability influence re-queries the first pool (`Q9 partners, tile 1 (rebalanced)`, or `near venue (rebalanced)`) without it and merges by rank. On the fixture world only bills of unrelated acts trigger it, and those also fail the split-half check, so it runs on the near-venue pool.
6. **Narrate.** `@walkup/narrator` (the template without a model). Narrator inputs carry only citable numbers: top tiles, partner count, budget shares and the what-ifs. On a genre tag baseline the narration names the genre's fans instead of "the room's usual crowd" (`honestWording` with `genreBaselinePhrase`: "country fans in general" on G1-A when the house heatmap fails, "fans of this genre in general" when the bill has no genre), and the sponsor is called local only when the `brandLocationMoves` probe is on; with no lift map at all the template's "No area stands out on this run" reads "There is no lift map on this run", as the partners card's reason does (word changes only, after the guards).
7. **Guards.** Operator lines pass the narrator's guard. Fan-facing copy hooks also pass `@walkup/engine` `validateNarration` with the all-ages alcohol rule. Alcohol tags are held back from the allowlist on shows that are not 21+ or that the operator set to all ages. Every entity on the sheet is sanitized (persons lose all tags, others lose denied tags); the receipt line reads "N tags denied by policy (ethnicity/inclusivity/credit_card)", and `guard.deniedByNamespace` carries the same counts per class (no tag names). Partner lines whose entity does not trace to a ledger entry are dropped and counted.
8. **Sheet extras**, from data the run already has (no Qloo calls, never the model; rules and wording in `@walkup/engine` `steps.ts`, `explain.ts`, `discovery.ts`):
   - **Why this place** (`steps/explain.ts`): every partner gets `explain` before the partners card streams: its tags (bill's own tags first, then tags shared across the list; category, denied and, unless adults only, alcohol tags left out), area (tile name, else the gazetteer at its location), straight-line km from the venue, one ask from the category table (a pre-show listening night only when Ticketmaster says 21+ and the operator has not said all ages), confidence with a one-line reason (pool size from the ledger, widened radius or categories, hours for the street-team day, near-venue list, thin signal), the limits line and its receipts (pool, house twin).
   - **Steps** (`steps/trace.ts`, `sheet.steps`): one plain decision per step, added as the run reaches it: pause (when a name was picked, or still waits), acts, the room's usual crowd, lift map, map check (split-half and foot traffic), partners, usual-crowd overlap (the places the ubiquity penalty pushed off, found by replaying the scoring without the house twins), popularity check (the number, or why there is none), your list, before and after, podcasts and sponsor, summary and checks. Fallen-back and skipped steps stay in the list with the reason. Every number comes from the sheet (card fields and summaries, ledger counts and parameters, the lift diagnostics) and every ref from this run's ledger.
   - **Discovery** (`steps/discovery.ts`, `sheet.discovery`): the partner rule first (room's own crowd as the baseline); then the area rule, only on a map that passed its checks (room's own crowd as the baseline, split-half above 0.5, lift not following foot traffic, heatmap not thin); else none. On the fixture world: G1-A, G1-B and G2 get a partner, G3 (no lift map) none.

## The revise loop (`src/revise/`)

An operator's note about a finished sheet ("All ages: no bars", "skip Germantown", "only Saturday", "within 10 km") becomes a new sheet under a new plan id.

```ts
import { parentRequest, revisePlan } from "@walkup/orchestrator";

const parent = { sheet, request: parentRequest(sheet, { stored: stored?.request, presetId }) };
const r = await revisePlan(parent, "All ages: no bars", deps, { onStep, onCard });
if (r.status === "question") show(r.revision.question);   // nothing changed, nothing ran
else r.result.sheet.revision;                              // { parentPlanId, instruction, interpreter, toolCalls, changes }
```

1. **Read** (`readInstruction`). `reviseSummary(sheet)` builds the compact view (show facts, settings, the areas on the sheet: lift tiles at or above the lift floor plus every partner tile, and the place-type keys with counts; no partner names, no contacts). `@walkup/narrator` `readRevision` turns the note into tool calls: the model through `deps.narrator.client` (and its spend guard) when one is set, otherwise the fixed rules (`interpreter: "rules"`). A question (`ask_operator`, or a note the rules can't read) stops here: `status: "question"`, `questionRevision(reading)`, no run, nothing stored. Model calls are written to a ledger of their own and copied into the revised sheet's ledger (`L1`, ...; note `node revise; revise turn 1; ...`).
2. **Overrides** (`overridesFor`). `set_all_ages` -> `allAges`; `exclude_partner_categories` and `exclude_areas` add to the parent's exclusions; `set_street_team_days` and `set_radius` replace. Nothing else changes.
3. **Re-run** (`runRevision`). `parentRequest` rebuilds what the parent ran: its stored request; a preset by its event (the event id, date and inputs of the preset's show in the parent sheet's mode, its seed plan and paired plan, never `presetId`, so a revision is never stored or served as the preset); names the parent paused on keep the parent's pick (`pausePicks`, read from the parent's pause steps), so a revised G2 does not stop to ask again. `planShow` runs on the same deps with `serveFromStoreWhenGuarded: false`, so every Qloo request whose inputs did not change comes from the cache. On the fixture world: "no bars" sends 0 Qloo calls; "All ages: no bars" on G1-A (a 21+ bill) sends 10: the 9 partner calls (3 pools, their house twins and their popularity twins), because all ages also adds the night-club exclusion to the request, and the sponsor pick, which now leaves out alcohol, tobacco and gambling brands; "skip <area>" sends the 3 calls for the one pool that moved; a radius change re-sends the heatmaps, the room's usual-crowd maps included, the partner searches and the 2 pick-list searches for your declared partners ("within 10 km" on G1-A: 20). Venue-level calls stay cached in the other three.
4. **Mark** (`opts.revise` in `planShow`). The `revise` step goes first in the step stream (and through `onStep`): "Changed 2 settings from your note "All ages: no bars"." with who read it and which tools they chose, citing the model calls. Before the sheet is stored, `sheet.revision` is filled: `parentPlanId`, `instruction`, `interpreter`, `toolCalls` (each with its one-line summary) and `changes` from `diffSheets(parent, sheet)`: settings, then areas, partners and pre/post spots (removed first, then added). A removed row says why when the new settings explain it ("left out by type (all-ages show)", "its area was skipped", "closed Saturday, now the only street-team day", else "dropped when the list was rebuilt", with "; higher-ranked bars filled the area's 2 places" when its kind was full). Receipts point at the revised sheet's own ledger: an added row cites the calls that returned it, a removed row the new search; setting rows cite the model call (none when the rules read the note).

What the three new inputs do in the run (the steps say so): `allAges` drops every bar category from the partners and from the pre/post spots before the spots are picked (so the list fills from the rest), adds the night-club exclusion to the partner requests, and keeps the listening-night ask off partner explanations; `excludeCategories` drops those place types from both lists; `excludeAreas` leaves those tiles off the top list and out of the partner pools, and the discovery never picks them. The partners and before-and-after steps say "Left out N places by type (all-ages show)"; the lift step says "Left out N areas at your request".

Every call writes a ledger entry; the run ledger adds the node (`node Q9 partners, tile 2`) and, in fixture mode, `fixture world: synthetic response`. `PlanResult.budget` reads the ledger back: Qloo calls sent vs cached, bill-level vs venue-baseline (Q2, Q3, Q5, Q6, Q10 twin, the house halves of the split-half check). The trust checks are counted inside those totals but kept apart in the tests and the product eval: at most 4 split-half heatmaps (2 bill-level, 2 venue-level), at most 3 partner house twins and at most 3 partner popularity twins (bill-level), so at most 10. On the fixture world: a cold G1 run sends 16 bill-level and 6 venue plan calls (the signal check included) plus 10 checks (24 + 8). G2 sends 39 fresh calls across the pause (8 before the pick, 31 after it). G3 (a comedy club whose roster does not resolve: no lift map, so no split-half, Q6 or house twin calls, and partners from the near-venue pool) sends 16, its one popularity twin included, with its two fallbacks (the 60 km heatmap and the 2,500 m spots) on their cards. The month guard covers the twins like any call: below the floor a twin is refused, and the check is skipped with the reason.

When the Qloo month guard has tripped, a preset is served from the last stored sheet (`servedFromStore: true`); other runs use whatever the cache holds, and refused nodes show `degraded` with the quota reason.

## Fixture sheets

```sh
npx tsx packages/orchestrator/scripts/generate-fixture-sheets.ts            # writes fixtures/synthetic/engine/<id>.sheet.json
npx tsx packages/orchestrator/scripts/generate-fixture-sheets.ts --out /tmp/sheets
```

Each file is a fixture wrapper (`synthetic: true`, `fixtureId`, `title`, `note`, `pairedWith`, `budget`, `sheet`). The script refuses to write into `fixtures/synthetic/` itself (compared through symlinks and, on Windows, without regard to case), so the hand-built sheets stay as they are. The G2 pause is answered the way an operator would (the comedian candidate), and the note says so.

## Known limits

- Steps are built from the run's results after each part finishes, so they stream in step order but a part that is still running shows nothing yet. The web server forwards `onStep` as SSE `step` events.
- Revisions change five operator inputs only. On a 21+ bill marked all ages, the copy step holds alcohol tags back and the sponsor pick excludes alcohol, tobacco and gambling brands, the same as on an all-ages show; Ticketmaster's rule still applies when it is stricter.
- `pausePicks` finds the paused act by its name in the pause step's sentence; a bill with two acts whose names contain each other prefers the longer name.
- Live mode ran on Oct 21 2026: four real Ticketmaster bills, g1-a and g1-b at The Anthem, Washington DC (Rhiannon Giddens, Sun Feb 28 2027; FLO, Wed Feb 17 2027), and g4-a and g4-b at The Salt Shed, Chicago (Greensky Bluegrass, Wed Dec 30 2026; The Roots, Fri Jan 15 2027). The hosted site serves those runs and their recorded revisions in recorded mode. g2 and g3 have no live show, so a live run of g2 or g3 stops with `NO_LIVE_SHOW`.
- `config/tags.json` pins 11 of 14 categories (Oct 15). Record store, Irish pub and place of worship are dropped, so cards that ask for them say they were skipped. No genre baseline, sponsor exclusion or comedian tag is pinned yet. Fixture runs use `WORLD_TAG_PINS`.
- The world's tag pins still list a comedy baseline; `baselineTagFor` ignores it for comedy bills, as it would a live pin.
- Q9 filters hours by the first street-team day only; the engine double-checks the same day.
- Partner rows carry a lift-tile chip, the usual-crowd chip from the pool's twin ("ranks 3 places higher here than for the room's usual crowd") and, when one seed clearly leads, a "most influenced by" chip. The lift-tile chip still prints lift as "1.62x"; with the bounded score that is a ratio of smoothed percentiles, not a count.
- Thresholds (thin popularity 0.35, bill floor 0.7, split-half 0.5, ubiquity penalty up to 0.5 over half a list, 3 km tile spacing, outing rate 0.2, assumed capacity 120) are hand-picked, like the engine's lift parameters. KG2 on real heatmaps is the check.
- The split-half check splits seeds, not audiences: a bill whose acts draw different crowds fails it even when each act's map is sound. The card then says the halves disagree and ranks partners near the venue.
- No comparison arm runs, so `budget.arms` and `budget.places` stay 0 (both kept so stored plans keep their shape). A preset served from the store loses any Google Places list an older stored sheet carried (`withoutControl` from `@walkup/contracts`).
- The choice store is shared by every run that uses it. A public deployment should give each operator (or session) its own `ChoiceStore`, so one visitor's pick is never another visitor's silent default.

## Numbered areas

`spreadTiles` keeps top tiles at least 3 km apart and never two that share a ZIP, so areas 1-5 are distinct places;
`disambiguateNames` then gives clashing gazetteer names a distance and direction from the venue
("Nashville-Davidson, 17 km west", then a ZIP if that still clashes). Partners, the budget split, narration and the
web and print numbering all use these tiles. On a genre-tag baseline the steps, narration and card copy name the genre
("comedy fans in general", `genreBaselinePhrase`). The split-half check without two house halves compares the bill
halves with a partial Spearman (the shared house rank taken out), so a shared denominator cannot make noise agree.
